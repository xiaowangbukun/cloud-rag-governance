# Nginx 反向代理配置与 502/504 排查

## 1 适用范围

本手册面向把 Nginx 作为七层反向代理/负载均衡的部署形态，覆盖 `502 Bad Gateway`、
`504 Gateway Timeout`、`499 Client Closed Request` 三类高频故障，以及上游连接池、
超时参数、keepalive 的正确配置方式。适用 Nginx 1.18+（含 openEuler/Debian 发行版包）。

前置假设：Nginx 与上游（Java/Go/Node 服务）之间是 HTTP/1.1 短连接或长连接；
若使用 HTTP/2 或 gRPC，请额外查阅 `grpc_pass` 与 `http2` 相关章节。

## 2 最小可用反向代理配置

```nginx
upstream app_backend {
    least_conn;                                  # 上游节点性能不均时优于默认轮询
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 64;                                # 与上游保持长连接，降低握手开销
    keepalive_timeout 60s;
    keepalive_requests 1000;
}

server {
    listen 80;
    server_name app.example.internal;

    client_max_body_size 20m;                    # 上传大文件必须显式放开
    client_body_timeout 30s;

    location /api/ {
        proxy_pass http://app_backend;
        proxy_http_version 1.1;                  # keepalive 必须配 1.1
        proxy_set_header Connection "";          # 清掉 close，才能真正复用连接
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 3s;                # 建连超时：短，快速摘除坏节点
        proxy_send_timeout 30s;
        proxy_read_timeout 60s;                  # 读超时：按业务 P99 设置
        proxy_next_upstream error timeout http_502 http_503;
        proxy_next_upstream_tries 2;
    }
}
```

三个最常配错的点：

1. `proxy_http_version 1.1` 与 `proxy_set_header Connection ""` 必须同时出现，否则
   `keepalive` 无效，每请求都新建 TCP 连接，上游 TIME_WAIT 飙升。
2. `proxy_next_upstream` 默认不包含 `http_502`，上游返回 502 时 Nginx 直接透传给客户端，
   不会重试下一个节点。
3. `proxy_read_timeout` 默认 60s，长轮询/导出任务会被 504 打断，需按业务单独放开。

## 3 日志与状态码定位

### 3.1 关键日志字段

```nginx
log_format upstream_debug '$remote_addr "$request" $status '
                          'upstream=$upstream_addr '
                          'us=$upstream_status '
                          'rt=$request_time urt=$upstream_response_time '
                          'ct=$upstream_connect_time '
                          'ua="$http_user_agent"';
access_log /var/log/nginx/access.log upstream_debug;
```

解读：

- `urt`（`upstream_response_time`）接近 `proxy_read_timeout` → 超时类故障（504）。
- `ct`（`upstream_connect_time`）> 1s → 上游建连慢，通常是上游 accept 队列满或网络丢包。
- `us=502` + `urt` 极小（毫秒级）→ 上游主动重置连接或端口无人监听。
- `upstream_addr` 出现多个、用逗号分隔 → 触发了 `proxy_next_upstream` 重试。

### 3.2 按状态码分流

| 状态码 | 语义 | 先查什么 |
|---|---|---|
| 502 | 上游返回非法响应 / 连接被重置 / 无人监听 | 上游进程存活、端口监听、应用日志 |
| 504 | 上游在超时内未响应 | `urt` 分布、上游线程池、慢 SQL |
| 499 | 客户端先断开 | 上游响应过慢导致前端超时、移动端弱网 |
| 413 | 请求体超限 | `client_max_body_size` |
| 503 | 无可用上游 / 主动限流 | `upstream` 全部 `max_fails` 熔断、`limit_req` |

## 4 502 排查

### 4.1 判定标准

访问日志 `status=502`，且 `upstream_status` 为 `-`（未拿到响应）或 `502`（上游自己返回）。

### 4.2 处置步骤

```bash
# 1. 上游进程是否在监听
ss -lntp | grep 8080

# 2. 从 Nginx 所在机器直连上游，确认不是 Nginx 到上游的网络问题
curl -sv --max-time 3 http://10.0.1.11:8080/healthz

# 3. 看上游应用日志是否出现 connection reset / 线程池拒绝
journalctl -u app --since "10 min ago" | tail -50

# 4. 看 Nginx error.log 的具体错误
tail -200 /var/log/nginx/error.log | grep -E "connect\(\) failed|reset by peer|no live upstreams"
```

常见错误文本与对应根因：

- `connect() failed (111: Connection refused)`：上游没监听或刚重启，端口未就绪。
  处置：确认启动顺序与 readiness，或把 `proxy_connect_timeout` 调到 3s 并依赖重试。
- `recv() failed (104: Connection reset by peer)`：上游主动 RST。多为上游 `keepalive_timeout`
  小于 Nginx 的 `keepalive_timeout`，Nginx 复用了已被上游关闭的连接。
  处置：让 **Nginx 侧 keepalive_timeout 小于上游侧**（例如 Nginx 50s，上游 60s）。
- `no live upstreams while connecting to upstream`：全部节点被 `max_fails` 摘除。
  处置：`max_fails=3 fail_timeout=10s` 对抖动敏感的场景应放宽为 `fail_timeout=30s`，
  并用 `/healthz` 做主动探测而不是只靠被动失败计数。

### 4.3 上游 keepalive 的经典坑

Nginx `keepalive 64` 表示每个 worker 与每个上游保持最多 64 个空闲连接。
若上游是 Tomcat，`maxKeepAliveRequests` 默认 100，达到后服务端关闭连接，
而 Nginx 仍认为连接可用 → 下一个请求必然 502/连接重置。

处置：上游 `maxKeepAliveRequests` 调到 1000 以上，或 Nginx 侧降到明显更小的
`keepalive_requests`，让 Nginx 先主动关闭。

## 5 504 排查

### 5.1 判定标准

访问日志 `status=504`，`urt` 接近 `proxy_read_timeout`（如 60.001）。

### 5.2 区分「慢」与「卡死」

```bash
# 统计最近 1000 条请求的 urt 分布（秒），观察尾部
awk -F'urt=' '{if (NF>1) {split($2,a," "); print a[1]}}' /var/log/nginx/access.log | tail -1000 | sort -n | tail -5

# 上游是否在处理：抓包看有没有响应
tcpdump -i any -nn -A 'tcp port 8080 and host 10.0.1.11' -c 50
```

- 有响应但慢 → 应用侧慢（慢 SQL、锁等待、GC 停顿、下游依赖超时）。
- 完全无响应 → 应用线程池耗尽或死锁，需抓线程栈：

```bash
# JVM
jstack -l <pid> > /tmp/jstack.txt && grep -c "java.lang.Thread.State: BLOCKED" /tmp/jstack.txt
# 看连接池等待
jstack -l <pid> | grep -A3 "HikariPool\|DruidDataSource"
```

### 5.3 参数调整原则

- `proxy_read_timeout` 不是越大越好：它决定坏请求占用 worker 连接的时长。
  合理做法是按接口分级，而不是全局调到 600s：

```nginx
location /api/quick/ { proxy_read_timeout 10s; }
location /api/export/ { proxy_read_timeout 300s; proxy_buffering off; }
```

- 导出/流式接口必须 `proxy_buffering off`，否则 Nginx 会攒满 buffer 才开始回传，
  客户端表现为「长时间空白后突然全部出现」。
- 上游 504 与客户端 499 常常同时出现：客户端浏览器/网关先超时断开，
  Nginx 记为 499，随后上游返回被丢弃。**优化目标是降低 P99，而不是延长超时**。

## 6 499 与限流

### 6.1 499 的定位

`499` 是 Nginx 自定义状态码：客户端在 Nginx 返回响应前关闭了连接。
出现大量 499 时，问题通常在**客户端侧的上一跳**（浏览器、移动端 SDK、SLB、API 网关）
把超时设得比 Nginx 的 `proxy_read_timeout` 小。

处置：

1. 对齐超时链路：客户端超时 > 网关超时 > Nginx `proxy_read_timeout` > 上游处理时间。
2. 对确实需要长耗时的接口改为异步任务 + 轮询，避免占住连接。

### 6.2 限流保护上游

```nginx
limit_req_zone $binary_remote_addr zone=api_rl:10m rate=20r/s;
limit_conn_zone $binary_remote_addr zone=api_conn:10m;

location /api/ {
    limit_req zone=api_rl burst=40 nodelay;
    limit_conn api_conn 20;
    limit_req_status 429;
    limit_conn_status 429;
    proxy_pass http://app_backend;
}
```

`burst` 用满后超出 `nodelay` 的请求直接 429，不要配成无限排队 —— 排队只会把 502/504 变成
超时雪崩。

## 7 配置校验与灰度

```bash
nginx -t                          # 语法与证书校验，必须每次 reload 前执行
nginx -T | grep -n "proxy_read_timeout"   # 确认最终生效的配置（含 include）
nginx -s reload                   # 平滑重载
```

灰度顺序：改单台 → `nginx -t` → reload → 观察 5 分钟 `us=502/504` 比例 → 再推其余节点。
reload 期间旧 worker 会处理完存量请求再退出（`worker_shutdown_timeout` 默认无限），
所以长连接场景需要显式设置 `worker_shutdown_timeout 30s;`，否则滚动发布会挂住。

## 8 交接条件

- 需要修改上游应用线程池/连接池配置；
- 需要变更 SLB/网关层的超时或健康检查策略；
- 502/504 比例超过 1% 且持续 10 分钟以上，需按故障流程升级并保留
  `access.log` 与 `error.log` 对应时间窗的切片。
