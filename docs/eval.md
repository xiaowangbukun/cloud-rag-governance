# 检索评测基线（P0-2 → 决策级）

## 这份基线回答三个问题

1. **检索会不会把不该给的分片给出去？** 逐条命中对照独立算出的授权边界复核，
   得到 `unauthorized_leak_rate`。
2. **改了检索之后召回有没有变差？** 固定 74 题金标准，记录
   `recall@3 / recall@8 / MRR` 以及分维度切片，用 `--compare` 与历史基线比对。
3. **这些数字能不能当决策依据？** 报告自带 `decision_grade.blockers`（机器可读代码
   + 人话理由）；`--require-decision-grade` 时不达标退出码 4。

前两个问题问的是「安不安全、有没有退步」，第三个问的是「数据可不可信」。
**三者必须分开回答**：一份「零泄漏 + 召回 1.0」的报告完全可以同时是「不可用」的，
因为语料太小、向量是降级实现。合并成一个笼统的「通过」会制造最危险的假绿。

## 怎么跑

```bash
# 需要已建库 + 种子（DEMO_SEED=true 或 bootstrap 已跑过）
python -m rg_api.eval                     # 打印指标；有泄漏时退出码 2
python -m rg_api.eval --write docs/eval-baseline.json
python -m rg_api.eval --compare docs/eval-baseline.json   # 变差时退出码 3
python -m rg_api.eval --hybrid            # 强制开启混合检索做对照
python -m rg_api.eval --require-decision-grade            # 不达决策级时退出码 4
python -m rg_api.eval --no-backfill       # 不补算缺失向量（默认会补）
```

`--no-backfill` 存在的原因：种子只写 `embedding_text`，向量由 `backfill_embeddings`
计算。不补的话检索命中 0 条，会得到「零泄漏 + 召回 0」的假绿——比不跑更糟，所以
默认补算并把条数记在报告 `setup.backfilled_chunks`。

### 退出码

| 退出码 | 含义 | 判定顺序 |
|---|---|---|
| 0 | 安全两道闸门全绿，且与基线比无回归 | — |
| 2 | 有未授权命中，或拒答正确率 < 1.0（**不安全**） | 最先判 |
| 3 | 与基线比对召回/拒答变差，或报告版本不一致（**退步**） | 次之 |
| 4 | `--require-decision-grade` 下报告自报数字不可信（**不可信**） | 最后判 |

顺序是有意的：先判「不安全」，再判「退步」，最后才判「数据不可信」。若把 4 放在
最前，一个安全的实现可能因为环境缺 embedding 服务就被判成失败，掩盖真正的安全
回归。CI 当前只跑 `--compare`（不启用 4），原因见下节「已知局限」。

### 决策级判定：当前只差真实 embedding

报告 `decision_grade.blockers = ["offline_embedding"]`，其余阻塞项都已消除：

| 阻塞项代码 | 含义 | 当前 |
|---|---|---|
| `offline_embedding` | 向量由离线降级实现产生，排序近似噪声 | ✅ 命中（本机无法消除） |
| `corpus_saturated` | 分片数 ≤ `top_k`，`recall@k` 是恒等式 | 已消除（54 > 8） |
| `corpus_too_small` | 分片数 < `top_k × 4`，排序质量测不出差异 | 已消除（54 ≥ 32） |
| `no_project_slice` | 题库没有项目内正向题，项目维度从未被测量 | 已消除（30 题） |

**必须说清楚的一点**：本机没有外网、没有 GPU、没有可用的 embedding 服务，
因此**本仓库产不出决策级召回数据**。上面两组数字只能证明「安全闸门与回归对照在
工作」，不能证明「检索效果如何」。要得到决策级数据，需在 `EMBEDDING_BACKEND=HTTP`
（BGE-M3 服务）环境下重跑 `--write`，届时 `blockers` 应为空、`decision_grade.recall=true`。

## 指标定义（写清楚避免误读）

- **未授权泄漏率** = 未授权命中数 / 全部命中数。判据独立于检索 SQL：项目内行要求
  「项目在授权集合内」且「密级 ≤ 该项目上限」，全局行只要求「密级 ≤ 用户上限」。
  检索漏写条件时这条会红。
- **拒答正确率** = 「越权题没有返回该越权对象的事实」的比例。越权题返回全局规则
  文档是允许的（规则不是该项目的秘密），返回该项目的实际内容才算失败。本系统没有
  生成环节参与评测，所以「拒答」指**检索没有证据**。
- **recall@k**：正向题里正确文档落在前 k 名的比例；`k` 取 3 与 `top_k`。
- **MRR**：正向题正确文档排名的倒数的均值。**已知口径瑕疵**：字段名沿用
  `mrr_at_10`，但检索只返回 `top_k=8` 条，实际最多统计到第 8 名。改 `top_k` 时
  这个键名必须一起改，否则读报告的人会以为看的是前 10 名。
- **切片（`slices`）**：`global` = 不带 `project_id` 提问的题，`project` = 带
  `project_id` 提问的题。合在一起的单一 recall 会掩盖「某一维度整体失效」——
  旧基线全是全局题，项目维度从未被测量过。
- **`hit_rate`**：正向题里至少命中一次的比例。它与 `recall@8` 在当前 `top_k=8`
  下恒等，保留它是因为改小 `top_k` 后两者会分离（命中但排在第 9 名之外）。

### 为什么语料下限是 `top_k × 4`

`recall@k` 只在「正确文档不是必然进前 k 名」时才有区分度。语料等于 `top_k` 时
（旧基线 6 分片 vs `top_k=8`）任何实现都拿满分，指标是恒等式而不是测量。取 4 倍
是让 `top_k` 至多覆盖语料四分之一——仍不算严格，但足以让「排序有没有变差」被观测。

`MIN_CORPUS_MULTIPLE = 4` 是**工程约定，不是统计显著性阈值**：它只保证指标不饱和，
不保证指标有置信区间。74 道题的样本量也谈不上统计显著，这一点不应被报告的语气掩盖。

## 语料从 6 → 54 分片：为什么必须连带改种子

旧语料是 6 份全局文档、每份 1 段，共 6 分片。它同时导致三个问题：recall 饱和、
越权题没有可泄漏的内容（所以「拒答正确率」测的只是「检索返回了空/全局文档」）、
项目维度完全无法测量。改动分三步：

1. **新增 16 份项目内文档**：4 个项目 × 4 篇（`prj_core_policy` / `prj_claim` /
   `prj_agent` / `prj_data`，后两个项目整体为 `L4_SECRET`），每篇用 Markdown `##`
   分三节。项目内文档只写治理规则，**不放项目金丝雀值**，否则「知识库泄漏」与
   「金丝雀泄漏」两类判定会互相污染。
2. **题库从 40 题扩到 74 题**：62 道正向题（32 道全局 + 30 道项目内）+ 12 道越权题。
3. **种子切块换成生产切块器**：原 `seed/demo.py` 用私有的 `_split_paragraphs`
   （按 ASCII `;` 硬切、约 260 字），与生产摄取的 `chunk_markdown` 不是同一套。
   评测语料与线上切块口径不一致，等于用另一套实现的行为做基线。现在种子与摄取
   都走 `chunk_markdown`，并记录 `section_path`（旧的私有切块函数已删除）。

`report_version` 因此升到 2（新增 `slices` 与 `decision_grade.blockers`），
旧基线（`report_version=1`）与新报告不可比，`--compare` 会直接拒绝。

## 历史口径（`report_version=1`，40 题 / 6 分片）

下面这组数字来自旧口径，**与当前基线不可比**，保留是因为它记录了评测当时查出的
两处静默降级。测量方法：保持语料不变，把修复前的实现替换回去再跑同一套 40 题。

| 实现 | recall@3 | recall@8 | MRR | 总命中 | 有命中的题 |
|---|---|---|---|---|---|
| 当时（两处都修） | 0.9375 | 1.0 | 0.8812 | 240 | 40/40 |
| 仅回退多样性配额 | 0.9062 | 0.9062 | 0.8594 | 80 | 40/40 |
| 仅回退空项目集早退 | 0.5 | 0.5 | 0.4844 | 126 | 21/40 |
| 两处都回退 | 0.5 | 0.5 | 0.4844 | 42 | 21/40 |

1. **空项目集早退**：`_candidate_ids_with_scope` 在 `allowed_project_ids` 为空时
   直接返回空候选，把 `project_id IS NULL` 的全局知识一并挡掉——而那正是没有项目
   授权的只读用户（种子里的 `viewer`）唯一该看到的内容。代价是当时 32 道正向题里
   16 道 0 命中。
   （`test_global_knowledge_is_reachable_without_any_project`）
2. **多样性配额误伤全局知识**：配额把 `project_id or "global"` 当成一个项目，
   全局知识结果上限恒为 `RAG_MAX_CHUNKS_PER_PROJECT`（默认 2），3 道题的正确文档
   全部落在配额之外。
   （`test_global_hits_are_not_capped_by_project_quota`）

两处修复都不改变任何授权判定，只影响「哪些该看到的行真的被看到」。

## 第三处修复：项目保底（靠单测守，不靠基线）

放开全局配额后出现过一次反向问题：`top_k` 较小时高分全局分片会把项目分片整段挤出
结果集，于是「在项目内检索拿不到项目自己的分片」，拼图防护按项目统计的覆盖率也不再
累积（实测于 `test_jigsaw::test_repeated_search_eventually_downgrades`，`top_k=6`
反复检索始终不触发降密级）。

修复方式是给「每个有命中的项目」保底 1 条，保底总数上限 `limit // 4`
（`SecureRetriever._apply_diversity`）。**基线的数字变化不足以守住这条改动**：
项目保底只在项目分片被打分压住时才生效，而离线向量下的排序噪声会随机掩盖它。
因此它的回归保护来自单测（`test_project_hit_survives_when_global_scores_are_higher` 等）
——**基线没有覆盖到的语义，必须有单测另守**。

## 已知局限（不掩盖）

1. **没有真实 embedding**：`blockers` 里的 `offline_embedding` 在本机无法消除，
   因此「决策级」判定只能证明门槛逻辑会随条件放开而转绿（`test_decision_grade_gate_opens_once_backend_is_not_offline`
   用打桩的向量实现验证这条通路，**它不证明效果**）。
2. **样本量**：74 题足够发现「项目维度整体失效」这类粗粒度问题，不足以支撑
   「比上一版好 2 个百分点」这种结论。
3. **`RAG_MAX_CHUNKS_PER_PROJECT=2` 的语义待决策**：它使单项目上下文最多看到
   2 个项目分片（每篇文档 3 分片）。本机实测放大到 100 不改变当前指标，但真实
   embedding 下这条配额是否会压低项目召回，本环境测不出来。**是否改成「只在多
   项目并行检索时生效」需要单独评估，本轮未改。**
4. **越权题覆盖不完整**：12 道越权题覆盖 4 个项目 × 3 类越权主体，但不是全组合，
   新角色或新项目上线后需要补题。

## 维护约定

- **改语料必须改题库**：`gold_set.json` 的正向题绑定 `seed/demo.py` 的
  `KNOWLEDGE_DOCS`（6 份全局 + 16 份项目内）。改标题或删文档会让基线永久红；
  `test_every_seed_document_has_at_least_one_question` 会先报出来。
- **改判据必须升 `report_version`**：否则新旧报告会被当成同一口径比对。
- **改题库格式必须升 `GOLD_SET_VERSION`**：它与 `report_version` 分开递增，
  因为「题库加题」不需要改报告字段。
- **CI 位置**：`.github/workflows/ci.yml` 的 `eval-gate` 作业执行
  `--compare docs/eval-baseline.json`；`--require-decision-grade` 暂不接入，
  原因是没有真实 embedding 服务的环境下它会恒定失败（见「已知局限」1）。
